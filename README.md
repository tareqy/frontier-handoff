# Frontier Handoff

Frontier Handoff is an open repository for testing whether explicit instructions, procedures, and failure analyses produced during temporary model access can improve the work of successor models.

The repository preserves prompts and raw outputs, records their provenance, separates editorial judgment from source material, and provides protocols for controlled comparison. “Handoff” is a hypothesis about transferring useful operational text. It is not a claim that text transfers a model's weights, latent capability, private reasoning, or product environment.

> [!IMPORTANT]
> **A model’s description of its own strengths, weaknesses, reasoning, or successor models is evidence to evaluate, not authority to accept.**

## Why this exists

Access to a particular model, mode, tool set, or product configuration can be temporary. Before that access changes, a user can ask the model to externalize procedures: how it interprets ambiguous requests, checks facts, allocates effort, critiques conclusions, or routes tasks. Those procedures may be useful to a later model.

They may also be generic, performative, costly, unsafe in some contexts, or fitted to the originating product. Frontier Handoff keeps the source record and turns the proposed procedure into a testable intervention. The relevant question is not “Did a strong model say this?” It is “Under documented conditions, did using this artifact change downstream performance, and at what cost?”

## What is included now

- one exact extraction prompt and one byte-preserved raw output with checksum;
- a preliminary Codex model critique kept separate from the source artifact;
- methodology for provenance, extraction, review, evaluation, and limitations;
- a proposed evaluation rubric and test-case specification;
- reusable prompt, metadata, case, comparison, and experiment templates;
- standard-library repository validation, tests, and a continuous validation workflow.

No curated derivative, protocol-complete human or cross-model review, model-routing protocol, failure map, benchmark run, experiment result, or reproduction is included yet.

## What the repository is designed to accept

- exact extraction, critique, handoff, and evaluation prompts;
- byte-preserved raw outputs and separately identified curated derivatives;
- human reviews and cross-model critiques that preserve disagreement;
- model-routing proposals and failure maps;
- preregistered test cases, run-level results, experiment reports, and reproductions.

The main collections are [prompts](prompts/README.md), [artifacts](artifacts/README.md), and [evaluations](evaluations/README.md). Project rules live in [methodology](methodology/provenance-standard.md) and [project principles](docs/project-principles.md).

## What it does not claim

This repository does not claim that:

- a source model was superior because a contributor described it that way;
- a model can reliably report its own internal reasoning or comparative ability;
- a polished instruction set encodes latent capability;
- human or cross-model review proves that an artifact works;
- one benchmark score generalizes across tasks, products, tools, or model versions;
- an experimentally tested intervention improved performance—negative, mixed, and inconclusive outcomes are valid results;
- checksums authenticate model identity or generation history. They establish content integrity only after the recorded observation point.

## Status and evidence legend

One maturity label hides important distinctions, so Frontier Handoff uses separate dimensions.

| Dimension | Label | Meaning |
| --- | --- | --- |
| Contribution stage | **Proposed** | A record is planned but no generated source is preserved yet; this is not an artifact `status`. |
| Content | **Raw** | Imported or generated bytes are preserved without editorial changes. |
| Content | **Curated** | A separately identified derivative has documented edits and parent records. |
| Lifecycle | **Superseded** | A newer artifact is recommended; the historical record remains. |
| Lifecycle | **Deprecated** | Use is discouraged for a documented reason; the record remains. |
| Review evidence | **Human reviewed** | A named human review exists under a stated protocol or scope. |
| Review evidence | **Cross-model reviewed** | A separately identified model critique exists; this is not independent factual verification by itself. |
| Evaluation evidence | **Experimentally tested** | At least one documented experiment ran. Metadata records claim support separately from a `beneficial`, `harmful`, `mixed`, `no-detectable-effect`, or `inconclusive` observed effect. |
| Reproduction evidence | **Independently reproduced** | A separate party repeated a defined experiment and reported the degree of agreement. |

Generated claims also carry a `claim_class`: `hypothesis`, `operational-proposal`, `experimental-result`, `reviewed-recommendation`, or `verified-finding`. The last label must be narrowly scoped to its evidence and is intentionally difficult to earn. See the [artifact lifecycle](docs/artifact-lifecycle.md) and [terminology](docs/terminology.md).

## Reproducing an experiment

Before running a comparison, read the [evaluation protocol](methodology/evaluation-protocol.md) and [rubric](evaluations/rubric.md). Then:

1. Copy the [test-case template](templates/test-case.md) and fix the task, permitted context, tools, scoring criteria, exclusions, and stopping rules before viewing treatment results.
2. Define at least two matched conditions: the same successor model without the handoff and with the handoff. Add the originating model only as an optional reference condition.
3. Record exact model identifiers, product/interface, reasoning mode, system instructions when shareable, tool access, context limits, sampling settings, dates, and treatment placement. Use `unknown` when a fact is unavailable.
4. Randomize order and blind evaluators to condition where feasible. Use repeated trials because one completion is not a stable estimate.
5. Preserve run-level prompts and outputs. Record failures, exclusions, latency or token cost when available, and negative or inconclusive results.
6. Score every preregistered rubric dimension, report evaluator disagreement, and keep outcome separate from the fact that testing occurred.
7. Write the report with the [experiment template](templates/experiment-report.md), link parent artifacts and cases, and run repository validation.
8. For a reproduction, state every deviation from the original setup and report whether individual findings reproduced, failed to reproduce, or remained inconclusive.

## Contributing

Contributions may propose a prompt, preserve a raw artifact, add a critique, submit an evaluation, report a reproduction, dispute a conclusion, or correct metadata. Start with [CONTRIBUTING.md](CONTRIBUTING.md) and the relevant issue form.

Raw history is append-only: never rewrite an existing raw artifact. Corrections belong in metadata events, review notes, or a new derivative with a parent reference. Do not submit secrets, private system prompts you cannot publish, personal data, confidential conversations, customer material, or proprietary code without permission; see [SECURITY.md](SECURITY.md).

Run the local checks before opening a pull request:

```sh
python3 -m unittest discover -s tests -v
python3 scripts/validate_repository.py
```

The validator uses only the Python standard library and enforces the repository's documented metadata subset. Continuous validation also syntax-parses every YAML file and `CITATION.cff` using Ruby's standard YAML library. To mirror that check locally when Ruby is available:

```sh
find . -type f \( -name '*.yaml' -o -name '*.yml' -o -name 'CITATION.cff' \) \
  -not -path './.git/*' -print0 \
  | xargs -0 ruby -ryaml -rdate -e \
    'ARGV.each { |path| YAML.safe_load_file(path, permitted_classes: [Date, Time], aliases: false) }'
```

## Planned roadmap

These are proposed milestones, not completed results:

1. Define stratified factual, coding, ambiguous, casual, creative, and high-stakes benchmark cases.
2. Compare the first artifact against a no-handoff baseline using matched successor-model conditions and repeated trials.
3. Test Light, Standard, and Strict variants to measure reliability gains against rigidity, verbosity, latency, and refusal costs.
4. Ablate costly rules to identify which clauses change behavior.
5. Run independent reproductions across model versions and tool configurations.
6. Revisit machine-readable schemas or result indexing only after several real studies expose stable needs.
